# ApplyPilot Production Deployment

ApplyPilot is deployed as separate services:

```text
Browser -> Vercel React/Vite SPA -> Railway FastAPI -> Railway PostgreSQL / Redis
```

The browser calls the Railway API directly. JWTs remain in browser local storage and are sent with an `Authorization: Bearer` header; the API permits only the configured frontend origins and does not allow wildcard CORS.

## What is configured in this repository

- `frontend/src/api/client.ts` reads the public `VITE_API_BASE_URL` build variable. With no value, local Vite development continues to use `/api/v1` and its proxy.
- `frontend/vercel.json` rewrites SPA routes to `index.html`, so direct visits to `/applications` and `/applications/:id` work.
- The backend accepts both the existing `JOB_TRACKER_*` names and Railway-standard `DATABASE_URL`, `REDIS_URL`, `JWT_SECRET`, and `FRONTEND_ORIGIN`/`FRONTEND_ORIGINS` names.
- `postgres://` and `postgresql://` database URLs are converted to the `postgresql+asyncpg://` SQLAlchemy driver URL required by this backend.
- The backend Docker command listens on Railway's injected `PORT` (and retains port 8000 locally).
- Railway migrations are run as a pre-deploy command rather than by each web process, preventing concurrent application replicas from racing to migrate.

## Railway setup

1. In Railway, create a project and choose **New** -> **GitHub Repo**. Connect GitHub if prompted and select this repository.
2. Open the resulting backend service. In **Settings**, set **Root Directory** to `/backend`; Railway will then detect `backend/Dockerfile`.
3. Leave the Dockerfile build/start command in place. The Dockerfile starts `uvicorn app.main:app --host 0.0.0.0 --port $PORT`.
4. Create the data services from the project canvas: **New** -> **Database** -> **PostgreSQL**, then repeat with **Redis**. Keep their service names, or substitute their actual names in reference variables below.
5. In the backend service's **Variables** tab, add the following. Reference values are not copied secrets and track Railway's managed connection settings.

| Name | Value |
| --- | --- |
| `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` |
| `REDIS_URL` | `${{Redis.REDIS_URL}}` |
| `JWT_SECRET` | a new, high-entropy secret generated by you |
| `KIMI_API_KEY` | your Kimi server-side API key, if Company Intelligence is enabled |
| `FRONTEND_ORIGIN` | initially `http://localhost:5173`; add the Vercel production URL after Vercel deploys |

If your database services are not named `Postgres` and `Redis`, replace those tokens with the exact Railway service names. Do not set any of these values in Vercel or commit them to Git.

6. In the backend service **Settings** / deployment configuration, set **Pre-Deploy Command** to `alembic upgrade head`. It executes using the built image and backend variables before traffic reaches the new deployment.
7. In **Settings** -> **Networking**, set the healthcheck path to `/health`, then click **Generate Domain**. Copy the resulting `https://…up.railway.app` domain. Confirm `https://<domain>/health` returns success in a browser.
8. Return to the backend variables and change `FRONTEND_ORIGIN` to the exact Vercel URL once it is known. For more than one allowed origin, use `FRONTEND_ORIGINS` with comma-separated URLs, for example `http://localhost:5173,https://applypilot.vercel.app`.

## Vercel setup

1. In Vercel, click **Add New** -> **Project**, import this GitHub repository, and select it.
2. Before deployment, set **Root Directory** to `frontend`. Vercel should identify the framework as Vite.
3. In **Settings** -> **Environment Variables**, add `VITE_API_BASE_URL` with value `https://<your-railway-domain>/api/v1`. Select Production; optionally configure a Preview Railway API for preview deployments.
4. Deploy. The `vercel.json` in `frontend` supplies the SPA rewrite automatically.
5. Copy the production Vercel URL, place it in Railway as `FRONTEND_ORIGIN`, and redeploy the backend. Environment-variable changes only apply to new deployments.

## Post-deployment checks

1. Open the Vercel URL and exercise register, login, application CRUD, dashboard, guest mode, guest-to-cloud import, Company Intelligence, and offline read fallback.
2. In browser developer tools, confirm API requests use the Railway domain and contain no CORS errors.
3. Confirm Railway deployment logs show `alembic upgrade head` before the web process starts and that `/health` remains healthy.

## Secret safety

Never expose or commit `KIMI_API_KEY`, `JWT_SECRET`, `DATABASE_URL`, `REDIS_URL`, database credentials, or a `VITE_KIMI_API_KEY`/`VITE_JWT_SECRET`. `VITE_API_BASE_URL` is intentionally public because it is embedded in the frontend bundle.
